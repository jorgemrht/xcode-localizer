# Xcode Localizer

One job: create and update Xcode 26 String Catalog localization artifacts inside `Translations/`. App source is off limits unless the user explicitly accepts the post-apply repository review or explicitly accepts implementing proposed non-localized UI replacements.

## Runtime Requirements

- Requires Python `3.14+` to run `scripts/apply_xcstrings_changes.py`.
- On macOS, install it with Homebrew:

```bash
brew install python@3.14
python3 --version
```

- For local tests, use a project virtual environment:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install pytest
.venv/bin/python -m pytest tests/ -v
```

## Principles

| # | Rule | Why |
|---|------|-----|
| 1 | Check `Translations/` first, always | Prevents writing files to wrong locations |
| 2 | Never read app source or UI files without explicit review consent | Agent must not spend tokens or drift into view editing when asked for copy |
| 3 | Stable `{screen}_{element}_{meaning}` keys | Renames break existing `LocalizedStringResource` references |
| 4 | All-language coverage on new keys | Partial catalogs cause runtime fallback to key names |
| 5 | `AppStrings.swift` wraps `LocalizedStringResource` | `NSLocalizedString` bypasses String Catalog validation |
| 6 | No `extension LocalizedStringResource` in app target | Xcode auto-generates the same symbols → duplicate declarations |
| 7 | HTML report on every change | Human review of what changed, when, and by whom |
| 8 | Config in `xcode-localizer.config.json` | Settings persist across sessions without re-asking the user |
| 9 | `extractionState: manual` on every entry | Prevents Xcode from treating agent-written strings as stale |
| 10 | No JSON report files | HTML is human-readable; JSON reports are noise in the repo |
| 11 | Audit before write | Broken variants and placeholders must never reach the catalog |
| 12 | Ask before repository review | Missing translations, unused keys, and non-localized UI text require source scanning |
| 13 | Ask again before code changes | Proposed replacements must never be applied silently |

## Zero Rule

When the user asks for translations, screen text, placeholders, buttons, labels, or localized copy:

1. Do not locate screens.
2. Do not read or search Swift files.
3. Do not read the Xcode project.
4. Check only whether `Translations/` exists.
5. After a successful `apply`, ask the post-apply review question before any source scan.

If `Translations/` does not exist:

```text
Translations folder does not exist. Please tell me the path where I should create it.
```

Do nothing else until the user answers.

## Only Outputs

```text
Translations/Localizable.xcstrings
Translations/AppStrings.swift
Translations/xcode-localizer.config.json
Translations/reports/latest.html
Translations/reports/historyofchanges.html
Translations/reports/<dd-mm-yyyy-HHMMSS>-xcode-localizer.html
```

Post-apply repository review is the only exception. It is allowed only after the user answers yes to the review question, and it is read-only unless the user later accepts implementing proposed non-localized UI replacements.

If `Translations/L10n.swift` contains `Auto-generated by xcode-localizer`, delete it after writing `AppStrings.swift`.

Never create or modify:

```text
*.swift outside Translations/   *.xcodeproj/**   project.pbxproj
Package.swift   Tuist files   .strings   .stringsdict   .xcloc
JSON report files   .xcode-localizer.json   Translations/L10n.swift
```

## Hard Rules

- Do not read, search, inspect, diff, open, create, modify, or delete app source files, UI files, project files, target membership, build settings, or manifests unless the user explicitly accepts the post-apply repository review or explicitly accepts implementing proposed non-localized UI replacements.
- Do not modify views or connect views to localization keys unless the user explicitly accepts implementing proposed non-localized UI replacements.
- Do not infer screen names from source files. Use only the user's words.
- If `Translations/` is missing, stop and ask where to create it before running any script.
- If `Translations/Localizable.xcstrings` does not exist, create it.
- Generate HTML review reports every time localization text changes.
- `latest.html` title: `Xcode Localizer - Current localizations`. Show `Last time generated: <dd-mm-yyyy hh:mm:ss>` under the page title. Includes views: all keys, key pattern groups, screen groups, element groups, and key descriptions. The `Go To Key descriptions` button and the full ungrouped Key descriptions section are visible only in the All keys view. Key descriptions are also shown inside each key pattern, screen, and element group.
- `historyofchanges.html` shows change reports from most recent to oldest. Show `Last time generated: <dd-mm-yyyy hh:mm:ss>` under the page title. Render one table with `date`, `version`, `build`, and `author` columns, followed by a right-aligned review button column with no header text. Display dates as `dd-mm-yyyy hh:mm:ss`, not filenames. Include two filters next to `Current localizations`: a calendar date input and an author text input. If no rows match, hide the table and show centered text: `No localization text was generated for that date or author.`
- `historyofchanges.html` renders `date`, `version`, `build`, and `author` columns, followed by the right-aligned review button. Each change report persists its app version and build in HTML metadata. Resolve them from `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`, then from `appVersion` and `appBuild` in config; use `Unknown` only if neither source is available.
- Change report columns: `status`, `key`, language old/new pairs (`en old`, `en`, `es old`, `es`…), `author`.
- Current report columns: `key`, language columns, `author`. No `warnings`, `screen`, `element`, or `meaning` columns.
- `author` resolves: `GIT_AUTHOR_NAME` → `git config user.name` → last commit author → `Unknown`.
- Do not generate JSON reports.
- Preserve unknown fields in existing `.xcstrings` entries.
- Treat placeholder mismatches, missing fallback variants, and different variation shapes as errors. Do not write a partial catalog.
- Use `variations` for plural or device-specific copy. Do not flatten an existing variation into `stringUnit`.
- On a new key, provide translations for every language in config and every language already in the catalog.
- Write concise translator context in the top-level `comment` and concise per-language descriptions in each localization `comment`.
- Use `scripts/apply_xcstrings_changes.py` when a terminal is available.
- Do not use legacy localization formats.
- Do not integrate files into Xcode automatically.

## Key Convention

```text
{screen}_{element}_{meaning}
```

- `screen`: user-provided, snake_case. Default: `common`. Never infer from source.
- `element`: one of the configured `validElements` (see Default Settings).
- `meaning`: short English semantic identifier.
- All lowercase snake_case.

Good keys: `login_placeholder_username`, `login_button_sign_in`, `common_button_cancel`, `settings_title_notifications`.

Bad keys: `screen_btn_login`, `login_button_button`, `login_text_iniciar_sesion`, `login_label_1`.

## Swift API

Generate `Translations/AppStrings.swift` as a `LocalizedStringResource` wrapper grouped by screen:

```swift
AppStrings.Login.buttonSignIn
AppStrings.Common.buttonCancel
```

Do not use `NSLocalizedString`. Do not write `extension LocalizedStringResource` into the app target.

## Default Settings

```json
{
  "defaultLanguage": "en",
  "languages": ["en", "es"],
  "defaultScreen": "common",
  "appVersion": "",
  "appBuild": "",
  "validElements": ["accessibility_hint","accessibility_label","alert","button",
    "context_menu","empty_state","error","label","link","message",
    "navigation_title","picker","placeholder","subtitle","success",
    "tab","text","title","toggle","toolbar","warning"],
  "keyPattern": "{screen}_{element}_{meaning}",
  "swiftApiName": "AppStrings"
}
```

Create `Translations/xcode-localizer.config.json` when missing. Modify it only when explicitly requested.

## Change Contract

```json
{
  "defaultLanguage": "en",
  "items": [
    {
      "screen": "login",
      "element": "placeholder",
      "meaning": "username",
      "translations": { "en": "Username", "es": "Usuario", "it": "Nome utente" },
      "comments": {
        "en": "Login username placeholder.",
        "es": "Placeholder del usuario en login.",
        "it": "Placeholder nome utente nel login."
      }
    }
  ]
}
```

For deletion:

```json
{ "items": [{ "key": "login_placeholder_username", "delete": true }] }
```

For plurals or device-specific copy, use one `variations` tree per language. A tree has either `plural` or `device` at each level; nest them when both are needed. Every rule must include an `other` fallback. Leaves use `value`.

```json
{
  "items": [
    {
      "screen": "photos",
      "element": "text",
      "meaning": "selected_count",
      "variations": {
        "en": {
          "plural": {
            "one": { "value": "%lld photo selected" },
            "other": { "value": "%lld photos selected" }
          }
        },
        "es": {
          "plural": {
            "one": { "value": "%lld foto seleccionada" },
            "other": { "value": "%lld fotos seleccionadas" }
          }
        }
      }
    }
  ]
}
```

```json
{
  "items": [
    {
      "key": "common_button_continue",
      "variations": {
        "en": {
          "device": {
            "iphone": { "value": "Continue" },
            "mac": { "value": "Continue" },
            "other": { "value": "Continue" }
          }
        },
        "es": {
          "device": {
            "iphone": { "value": "Continuar" },
            "mac": { "value": "Continuar" },
            "other": { "value": "Continuar" }
          }
        }
      }
    }
  ]
}
```

Never mix `translations` and `variations` for a single item. When updating a key that already has variants, use `variations` so its Xcode structure remains intact.

## Workflow

1. Check whether `Translations/` exists. If not, ask where to create it and stop.
2. After confirmation, create `Translations/` and `Translations/Localizable.xcstrings` if needed.
3. Build the change JSON from the user request.
4. Audit the catalog without changing it:

```bash
python3 /path/to/xcode-localizer/scripts/apply_xcstrings_changes.py audit
```

The audit checks catalog structure, language coverage, variant shape, required `other` fallbacks, `stringUnit` states, and placeholders at every variant leaf. It also runs `xcstringstool` unless `--skip-xcode-validation` is explicitly necessary.

5. Run:

```bash
python3 /path/to/xcode-localizer/scripts/apply_xcstrings_changes.py apply \
  --allow-create-translations \
  --changes-json '<json>'
```

6. After a successful apply, ask exactly:

```text
Would you like me to check whether all app text is translated and whether any localization keys are unused in the code?
```

Do not run the repository review unless the user says yes.

7. If the user says yes, run the read-only repository review:

```bash
python3 /path/to/xcode-localizer/scripts/apply_xcstrings_changes.py repository-audit --source-root .
```

Then show a plain-text report with exactly these sections:

```text
Missing translations
- Key: profile_button_delete_account
  Missing languages: de
  Existing translations:
  - en: Delete account
  - es: Eliminar cuenta
  - fr: Supprimer le compte
  - it: Elimina account

Non-localized UI text
- File: /absolute/path/SettingsView.swift:42
  Text: Delete account
  Proposed key: settings_button_delete_account
  Proposed translations:
  - en: Delete account
  - es: Eliminar cuenta
  - fr: Supprimer le compte
  - it: Elimina account

Possibly unused localization keys
- settings_button_old_delete_account
```

For `Non-localized UI text`, replace any `[agent translation required]` placeholders from the CLI output with real proposed translations before showing the user. Use `Proposed key` and `Proposed translations`; do not print a generic `Reason` line.

8. If the report contains any `Non-localized UI text`, ask exactly:

```text
Would you like me to add the proposed localization keys and replace these texts in the code?
```

Only if the user says yes:

- Add the proposed keys to `Translations/Localizable.xcstrings` with the accepted translations by using the normal `apply` command.
- Replace only the exact source occurrences from the report with localized references.
- Do not perform global text replacement.
- Do not delete possibly unused keys automatically.
- Generate the normal HTML reports after adding the proposed keys.

9. Validate when Xcode tools are available:

```bash
xcrun xcstringstool print Translations/Localizable.xcstrings
xcrun xcstringstool compile Translations/Localizable.xcstrings \
  --output-directory /tmp/xcode-localizer-check --dry-run
```

## Comments

Use the `.xcstrings` `comment` field for translator context. Write explicit comments when supplied or reasonably derived from the user request. Do not inspect app source to generate comments.
